# 30/60/90: standing up a SAST/DAST program

The role: select and stand up SAST/DAST, onboard dev teams, and hand operational alerts to Security Operations. The approach: **run AppSec like a detection pipeline.** High-signal findings, automated routing to owners, and a runbook-backed SOC handoff. This lab (`appsec-rpg` + Juice Shop) is a working small-scale version of every step below.

## Days 1–30: Learn and baseline (no gates, no noise)

**Goal:** know what we have, who owns it, and what the scanners would say, without breaking a single build.

- Inventory: repos, languages, CI systems, deploy targets, internet exposure. Rank apps into tiers (Tier 1 = internet-facing or regulated data).
- Map ownership: CODEOWNERS coverage per repo; a named team for every Tier 1 app. *No owner, no routing.*
- Meet each Tier 1 team lead plus SecOps: current pain, release cadence, what "blocking" would cost them.
- Run the tool bake-off on 2–3 representative repos and one known-vulnerable calibration target (the Juice Shop pattern). Score with `tool-evaluation-matrix.md`.
- Turn on the free, zero-friction controls everywhere: secret-scanning push protection, Dependabot alerts.
- Baseline metrics: open findings by severity and tier, % repos scanned, % with an owner.

**Exit criteria:** tool decision signed off; a pipeline template (`security.yml` equivalent) proven warn-only on 3 repos under 5 minutes; a RACI agreed with SecOps.

## Days 31–60: Pilot and handoff (signal over coverage)

**Goal:** prove the loop end to end with 2–3 pilot teams: scan, triage, route, fix, measure.

- Roll the pipeline template to the pilot teams' Tier 1 repos (warn-only).
- Build the routing flow (SOAR: n8n/Tines): ingest SARIF/JSON → enrich (owner, tier, exposure) → dedupe → Jira with SLA → Critical-only to SIEM + chat. SOC gets **only** Critical, confirmed-actionable events, each with a runbook link.
- Write runbooks for the top alert types (exposed secret first), and drill one with SecOps.
- Hand-triage every new finding in the pilot for 2 weeks; record precision per rule; tune (path excludes, rule disables, custom rules for org-specific patterns such as missing ownership checks).
- Authenticated DAST against staging for the Tier 1 apps (nightly, from inside the network).
- Developer enablement: a 30-minute session per pilot team, plus "how to read and suppress a finding" docs.

**Exit criteria:** pilot findings flow to the right owner automatically; SOC has handled at least one drill alert via the runbook; per-rule precision known; pilot teams rate the noise as acceptable.

## Days 61–90: Gate and scale

**Goal:** turn on blocking where it's trustworthy, and expand coverage with the same playbook.

- Enable gating on **new** Critical/High findings from rules with ≥ 90 % precision (`gating-policy.md`), pilot teams first, with an exception process.
- Roll out to all Tier 1 repos, then Tier 2, in waves. Each wave runs warn-only for 2 weeks, then gates.
- Monthly report to engineering leadership: coverage, MTTR by severity, SLA breaches, precision, push-protection blocks.
- Backlog plan for pre-existing findings: risk-ranked (KEV/EPSS, exposure, tier), burned down through SLAs, not gates.
- Next-quarter roadmap: threat modelling for Tier 1, security champions, API inventory/DAST coverage, SBOM and supply-chain policy.

**Exit criteria:** 100 % of Tier 1 repos scanned on every PR; gate live on pilot teams with < 1 false block per team per month; MTTR baseline published.

## Metrics that matter

| Metric | Why |
|---|---|
| % of Tier 1 repos scanned on every PR | Coverage |
| Precision per rule (TP / triaged) | Trust; drives gating decisions |
| MTTR by severity; % within SLA | Is the loop actually closing? |
| New Critical/High introduced per month | Is shift-left working? |
| Push-protection blocks and bypasses | Secrets prevented vs. leaked |
| Pipeline duration p95 | Dev experience; keep under 5 min |
